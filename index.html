Cloud-Native FinCore

Une simulation de système bancaire repensée en architecture distribuée. Le but n'est pas seulement de traiter des transactions, mais de montrer une chaîne complète : code Java, images Docker, orchestration Kubernetes et provisionnement automatisé avec Terraform.

Voir le code sur GitHub ↗
TypeProjet personnel · 2025
Services3 microservices REST
LangageJava 17 · Spring Boot
DéploiementKubernetes via Terraform

Architecture

Chaque étape du traitement est un service indépendant. Les services se trouvent par leur nom DNS interne au cluster, sans adresse IP codée en dur.

Client · curlPOST /api/transaction → NodePort 30082

Essayer le flux

Cette simulation reproduit la logique des contrôleurs : le service de validation rejette toute transaction supérieure à 1 000, et seules les transactions validées partent au règlement.

# Choisissez un montant puis envoyez la transaction.

Ce que j'ai réalisé

  • Trois microservices Spring Boot (Transaction, Validation, Settlement) exposant chacun une API REST et un endpoint de santé via Actuator.
  • Communication inter-services avec RestTemplate : Transaction appelle la validation, puis le règlement si la transaction est acceptée.
  • Conteneurisation de chaque service avec son Dockerfile, et un docker-compose sur un réseau dédié pour tester les échanges.
  • Manifestes Kubernetes : Deployments, Services NodePort et ClusterIP, variables d'environnement injectées dans les pods.
  • Infrastructure as Code : manifestes YAML traduits en HCL avec le provider Kubernetes de Terraform, pour un déploiement sans intervention manuelle.
  • Résilience : sondes readiness et liveness pour que Kubernetes redémarre un service défaillant.

Extraits de code

transaction-service · TransactionController.java
@PostMapping("/api/transaction")
Transaction create(@RequestBody Transaction t) {
  RestTemplate rest = new RestTemplate();
  Transaction v = rest.postForObject(
      "http://validation-app:8081/api/validation",
      t, Transaction.class);
  if (v != null && "VALIDATED".equals(v.getStatus())) {
    return rest.postForObject(
        "http://settlement-app:8083/api/settlement",
        v, Transaction.class);
  }
  return v;
}

Ce que j'ai réalisé

  • Modèle de données Django : types de documents, documents avec fichier joint, historique des statuts et profils utilisateur à trois rôles (Contributeur, Valideur, Administrateur).
  • API REST avec Django REST Framework : ViewSets, sérialiseurs imbriqués et une action dédiée PATCH changer_statut qui enregistre l'historique.
  • Sécurité : authentification par token, accès refusé aux anonymes par défaut, et une permission personnalisée EstAdministrateur.
  • Front-end Angular en composants standalone : page de connexion, liste des documents en tableau PrimeNG, style Tailwind.
  • État réactif avec les Signals : le token est un signal, et la liste se recharge dès qu'il change.
  • Intercepteur HTTP et garde de route : le token est ajouté à chaque requête, et la page des documents est inaccessible sans connexion.
  • Tests : contrainte d'unicité, refus sans authentification et création d'un document avec fichier.

@action(detail=True, methods=['patch'])
def changer_statut(self, request, pk=None):
    document = self.get_object()
    ancien_statut = document.statut
    document.statut = request.data.get('nouveau_statut')
    document.save()

    if ancien_statut != document.statut:
        HistoriqueStatut.objects.create(
            document=document,
            ancien_statut=ancien_statut,
            nouveau_statut=document.statut,
            modifie_par=request.user,
        )
    return Response({'statut': document.statut})

Recherche · Sécurité · Master 1

La blockchain est-elle le moyen le plus sûr de sécuriser des données ?

Un sujet de recherche sur les mécanismes de la blockchain et son potentiel comme stockage externalisé. Après un état de l'art, j'ai testé la question par l'expérience : modifier des blocs d'une chaîne écrite en C, puis vérifier si l'altération passe inaperçue.

Voir le dépôt et la présentation ↗
TypeInitiation à la recherche
NiveauMaster 1 · 2022
LangageC · SHA-256
LivrablesArticle · soutenance

Reproduire l'expérience

Chaque bloc garde l'empreinte SHA-256 du bloc précédent. Modifiez la valeur d'un bloc, comme avec alterNthBlock, puis lancez la vérification de la chaîne. Les empreintes sont calculées en direct dans votre navigateur.

$ ./a.out
1)addNewNumber  2)alterNthBlock  3)printAllBlocks  4)verifyChain

Démarche

  • État de l'art : articles de chercheurs, fonctions de hachage cryptographiques et fonctionnement d'une base de données distribuée en blocs.
  • Étude de code existant dans plusieurs langages, puis choix d'une implémentation en C qui permet d'inspecter la signature de chaque bloc.
  • Expérience : ajout de blocs, altération du ne bloc comme le ferait un utilisateur malveillant, puis vérification de toute la chaîne.
  • Résultat : la modification d'un bloc casse le lien avec le suivant, et la vérification la détecte immédiatement.

Conclusion

Points forts
  • Décentralisation : pas de point unique de défaillance
  • Signatures : toute modification est détectable
  • Plus besoin de tiers de confiance
Limites
  • Consommation d'énergie très élevée
  • Sécurité qui dépend du nombre de mineurs
  • La confiance se reporte sur le réseau

carte1.c · passage du terminal en mode brut


void change_mode() {
  static struct termios *save = NULL;
  if (save == NULL) {               // vers le mode non canonique
    struct termios *non_can = malloc(sizeof(struct termios));
    save = malloc(sizeof(struct termios));
    tcgetattr(0, non_can);
    tcgetattr(0, save);
    cfmakeraw(non_can);
    tcsetattr(1, 0, non_can);
    free(non_can);
  } else {                          // retour au mode canonique
    tcsetattr(1, 0, save);
    free(save);
    save = NULL;
  }
}
